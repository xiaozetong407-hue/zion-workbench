## 0. 结论速览

- 业务数据**唯一真值** = `localStorage['zion-data-v1']`（已 100% 确认，含 `_seeded` 播种标记）。
- 白屏事故的**工程根因**：`index.html` 被 Workbox **预缓存** + `cleanupOutdatedCaches:true` 清理旧哈希资源 → 旧 SW 返回旧 HTML 引用已被清理的旧 JS → 白屏。无痕/其他浏览器没有旧 SW，故正常。**与业务代码、数据无关。**
- 10 项需求**全部是 UI/统计逻辑改动，不需要改数据结构** → 不需要强制 migration，但需要建立 `schemaVersion` + 迁移框架 + 启动容错（防未来再出白屏）。
- 本轮**禁止**：unregister 现有 SW、清 Cache、动用户数据。SW 整改走「配置升级 + 新版本自然接管」，靠部署新版本来纠正，不在用户设备上执行任何删除。

## 1. 当前代码架构分析

### 1.1 技术栈

| 项 | 现状 |
|---|---|
| 构建 | Vite 5.4 + React 18 SPA，`base:'./'`，无 TypeScript（全 .js/.jsx） |

| 依赖 | react/react-dom/echarts/lunar-javascript（echarts 实际未被业务使用，历史遗留） |

### 1.2 目录职责

```
index.html          入口（vite-plugin-pwa 自动注入 registerSW.js）
src/main.jsx        挂载 <App/>
src/App.jsx         侧栏导航 + tab 路由 + 启动（sync.handleAuth→startSync）
src/styles.css      全部样式（~72KB 单文件）
src/utils/date.js   日期工具（todayStr/addDays/appDay/weekKey/monthKey/yearKey…）
src/store/db.js     业务 Repository：get/update(mutator)+ 全部领域读写方法
src/store/sync.js   Storage Adapter：缓存 + localStorage 落盘 + 可选 OneDrive 合并
src/store/onedrive.js  OAuth/上传（FILE_SYNC=false 时闲置）
src/store/useLive.js   订阅通知 hook
src/components/*    15 个页面组件
public/data-export.html  数据抢救页（纯静态，已上线同源）
```

### 1.3 数据层现状

- `db.js` 是**面向业务的 Repository 门面**（getCheckIn/setReview/addTask/getAllStatus…），所有方法走 `db.update(mutator)` → `sync.getCache()/setCache()`。
- `sync.js` 是**存储适配器**：`KEY='zion-data-v1'`，内存 cache + `readLocal()/writeLocal()`，未来换 IndexedDB 只需改它。
- `db.exportData()` 直接 `JSON.stringify(sync.getCache())`；`db.importData(json)` **直接覆盖 localStorage，无校验、无导入前备份、无读回验证**——这是数据安全的最大缺口。

### 1.4 直接读写 localStorage 的散点（重构边界）

| 位置 | key | 性质 |
|---|---|---|
| sync.js | `zion-data-v1` | **业务数据（唯一真值）** |
| Home.jsx | `zion-checkin-draft` | UI 草稿（非业务 blob） |
| Status.jsx | `zion-status-draft` / `zion-huawei-linked` | UI 草稿 / 状态标记 |
| Review.jsx | `zion-review-draft` | UI 草稿 |
| Reading.jsx / Past.jsx | `zion-weread-key` | 凭证 |
| onedrive.js | ClientId / Token | OAuth 凭证 |
| App.jsx | `zion-tab` | UI 状态 |

结论：业务 blob 的读写已集中在 sync.js，散点均为**非业务 UI 状态**，重构时保留（不入库），只需在文档中划定边界，不必强行搬入数据层。

## 2. 数据流分析

```
UI 组件 (Home/Tasks/Review/Status/Ledger/Reading/Past…)
   │  db.getXxx() / db.setXxx()
   ▼
db.js（业务 Repository，mutator 模式）
   │  sync.getCache()（读内存缓存，冷启动 JSON.parse localStorage）
   │  sync.setCache()（就地写内存 → writeLocal → schedulePush(空转)）
   ▼
sync.js（Storage Adapter）
   │  localStorage['zion-data-v1']（唯一真值）
```

**关键点：**
- 读路径：`load()` = `sync.getCache()`，首次访问时 `JSON.parse(localStorage.getItem(KEY))`，**解析失败时静默返回 `{}`（当前行为！）**——数据不报错，但会表现为「数据全空」。
- 写路径：`db.update(mutator)` 就地改内存 → `writeLocal` 全量序列化写入。**无校验、无读回、无失败回滚**。
- 启动播种：`db.ensureSeed()` 在模块加载时执行（`_seeded` 守护，仅首次写）。
- 备份/恢复：Me.jsx「数据备份」卡片 → `db.exportData()/importData()`（无验证）。

**本次重构后的目标数据流：**

```
UI 组件 → Repository（db.js：业务方法）
            │ loadData()/saveData()（安全写：读旧→拷贝→序列化→validate→写→读回→验证，失败不覆盖）
            │ exportData()（含 appVersion/schemaVersion/exportTime/统计）
            │ importData()（导入前自动备份当前数据 + 校验 + 失败回滚）
            │ validateData() / migrate()（schemaVersion 迁移链）
            ▼
Storage Adapter（sync.js，未来 IndexedDB 只改这一层）
            ▼
localStorage['zion-data-v1']
```

## 3. Service Worker / PWA 风险分析（本次事故核心）

### 3.1 当前配置与事故机制

```js
VitePWA({
  registerType: 'autoUpdate',
  workbox: {
    globPatterns: ['**/*.{js,css,html,svg,png,ico,woff2}'],  // ← html 被预缓存！
    globIgnores: ['**/data-export.html'],                    // ← 抢救页已排除 ✓
    cleanupOutdatedCaches: true,                             // ← 旧哈希缓存会被清
  },
})
```

**白屏链条（与现象完全吻合）：**
1. 旧版部署时，SW 预缓存了 `index.html` + 旧哈希 JS/CSS。
2. 新版部署后，旧 SW 仍控制页面（autoUpdate 需要下一次导航才换班）。
3. 用户打开 → SW 从 precache **直接返回旧 index.html**（不发网络请求）→ 旧 HTML 引用旧哈希 `index-*.js`。
4. 同时 `cleanupOutdatedCaches` 已把旧哈希资源从 cache 清掉 + 服务器上旧文件已被新构建覆盖 → 旧 JS 404 → **白屏**。
5. 无痕/其他浏览器：无 SW → 直接请求网络 → 拿到新 HTML+JS → 正常。✅ 全部现象解释。

### 3.2 保留 PWA 还是关闭？

**建议：保留 PWA（可安装），但按以下方式整改**——PWA 的收益（离线/安装）对个人工作台是真实价值，问题不在 PWA 本身，而在「HTML 预缓存 + 清理旧资源」的组合策略。

### 3.3 整改方案（逐条对应你的 10 条要求）

| # | 要求 | 方案 |
|---|---|---|
| 1 | HTML 导航 Network First | **index.html 移出 precache**（globPatterns 去掉 `html`），导航请求走 runtime `NetworkFirst`（成功即用新 HTML，网络失败才回退最近一次缓存 → 满足「网络失败降级旧版」） |
| 2 | 带 hash 的 JS/CSS 可缓存 | 保持 precache `{js,css,svg,png,ico,woff2}`（带 hash，更新即换名，天然安全） |
| 3 | 业务数据绝不进 SW Cache | 业务数据只存在于 localStorage；SW 不缓存任何 `/api` 请求（不配 runtime 缓存 for API） |
| 4 | `/data-export.html` denylist | `globIgnores` 保留 + `navigateFallbackDenylist: [/^\/data-export\.html$/]` 双保险 |
| 5 | 恢复页不得被 SPA fallback | 恢复模式若做成独立页（`/recovery.html`），同样加入 `navigateFallbackDenylist`；更稳妥：恢复模式做成 App 内组件（不依赖导航，天然不受 SW 影响） |
| 6 | 新旧 SW 更新策略明确 | 保持 `autoUpdate`（skipWaiting+clientsClaim）+ `cleanupOutdatedCaches:true`；HTML 改 NetworkFirst 后，发布即拿到新 HTML，旧 SW 危害窗口消失 |
| 7 | 避免长期被旧 SW 控制 | autoUpdate + NetworkFirst 已解决；不再需要用户手动清站 |
| 8 | 发布后可靠更新 | 每次部署 = 新 hash 资产 + 新 sw.js；客户端下次打开自动换新 |
| 9 | 网络失败降级旧版 | 导航 runtime NetworkFirst 的 cache fallback |
| 10 | 不允许 HTML 与 JS chunk 混用 | 核心保障：HTML 永不 precache、永远 NetworkFirst → HTML 与 JS 总是同代（同一份新 HTML 引用同一批新 hash 资源） |

### 3.4 必须遵守的底线

- **不在任何用户设备上执行** `unregister` / `caches.delete` / 清站操作。整改全部通过「发布新配置 → 新 SW 自然接管」完成。
- 用户设备上的旧 SW 会在下一次加载时被新 SW 替换（autoUpdate），此过程不动任何业务数据。

## 5. 推荐重构方案

### 5.1 数据层（第一阶段核心）

在现有 `db.js` + `sync.js` 基础上**增量加固**，不大拆大改（避免引入回归）：

1. **Storage Adapter（sync.js）**
   - 保留 KEY/内存缓存/readLocal/writeLocal。
   - 增加 `readRaw()`（读原始字符串，供恢复模式展示），`writeSafe(obj)`（序列化→写→读回→比对，失败抛错不落盘）。
   - 失败语义从「静默返回 {}」改为「标记 corruption → 触发恢复模式」。

2. **Repository（db.js 或新增 repository.js）**
   - `loadData()`：JSON.parse + `validateData()` + `migrate()`（迁移链，当前空转返回 v1）。
   - `saveData(data)`：安全写（读旧→浅拷贝→序列化→校验→写入→读回验证→失败保留旧值 + 记错误）。
   - `exportData()`：输出 `{ appVersion, schemaVersion, exportTime, statistics, data }`（保留向后兼容字段）。
   - `importData(json)`：**先自动把当前数据备份到 `zion-backup-last` key → 解析 → validate → 写 → 读回验证 → 失败自动回滚到备份**。
   - `validateData(data)`：顶层字段类型白名单校验（数组/对象/null 判定），返回 `{ok, errors}`。
   - `migrate(data)`：`data.schemaVersion ?? 1`；v1→v2 迁移函数表，逐版本升级，失败不落盘。
   - 业务方法（getCheckIn/addTask…）签名不变，内部改走 `loadData/saveData`，**页面组件零改动**。

3. **数据版本**
   - 写入时自动补 `schemaVersion: 1`（旧数据无此字段视为 v1）。
   - 10 项需求不需要迁移；框架就位，未来 v2+ 只加迁移函数。

### 5.2 启动容错（数据恢复模式）

- App 启动时（main.jsx / App.jsx 挂载前）`try { loadData() } catch`。
- 失败（JSON 解析失败 / schema 非法 / 迁移失败 / 字段类型异常）→ 渲染 **RecoveryScreen**（独立组件，不依赖任何业务模块）：
  - 【导出原始数据】读取 `localStorage.getItem('zion-data-v1')` 原始字符串，下载 .json（一字不改）。
  - 【导入备份】文件选择 → `importData`（内部先备份当前→校验→写入→验证）。
  - 【恢复上一次备份】从 `zion-backup-last` 恢复。
  - 【重试】重新 loadData。
- 只有校验通过才进入主应用 → **根除「数据/代码异常 → 白屏」**。

### 5.3 测试基建（项目当前无测试）

- 用 Node 22 内置 `node:test`（零新增依赖，ESM 直接可用）。
- `package.json` 增加 `"test": "node --test tests/"`。
- 新增 `tests/gamePeriod.test.js`、`tests/data-layer.test.js`（validate/migrate/export-import round-trip：导出→清空→导入→统计一致）。
- 纯函数放 `src/utils/gamePeriod.js`（不依赖 React/浏览器 API，node 可直测）。

### 5.4 SW/PWA（第七阶段）

见 §3.3 表，改动集中在 `vite.config.js` 的 workbox 配置 + 构建后自动检查（data-export.html 不在 precache、index.html 不在 precache）。

## 7. 回归风险清单（重点盯防）

| 风险点 | 场景 | 对策 |
|---|---|---|
| **任务字段污染** | addTask 改默认后误写旧任务 / editTask 波及时间字段 | addTask 只影响新对象；editTask 仅改 title；写单测断言旧任务 JSON 不变 |
| **拖拽交互破坏** | 手柄移除后长按区域与「点击编辑/勾选」冲突；列表滑动被吞 | 透明 hit-area 仅占左缘 24–28px；保留 preventDefault 与 MOVE_CANCEL 取消逻辑；真机 Android Chrome 手测 |

| **周周期边界** | 周一 23:59 vs 周二 00:01 翻转瞬间；跨月/跨年周（如 12-31 是周一）label 错位 | 纯函数单测覆盖 9 边界；label 用 `YYYY-MM-DD ~ YYYY-MM-DD` 全格式 |
| **状态统计** | 活动单位：数据是 exerciseMin（分钟）但标题写「小时」；不足 7 天平均；0 值被过滤；字符串数字 | 统一单位换算（分钟→小时保留 1 位）；平均=有记录的日期加权；Number() 强转 |
| **账本本年汇总** | 默认本年但只算了当月 / 跨年切换 | yearKey 过滤全自然年；默认 tab=本年 |
| **周报旧数据** | 旧 pastReports 带 wereadSec → 新 ReportViz 渲染报错 | 新 UI 不读 weread 字段；对旧结构防御式渲染 |
| **数据层重构** | ensureSeed 启动写入绕过安全写；import 覆盖前无备份 | 所有写路径统一走 saveData；import 强制先备份 |
| **SW 切换期** | 新部署后旧客户端过渡瞬间仍可能拿到旧 precache HTML | HTML 移出 precache 后该窗口消失；部署后用无痕+普通模式双验证 |
| **恢复模式死循环** | validate 失败但恢复模式本身读数据失败 | 恢复模式只读原始字符串（不 parse），不依赖数据层 |
